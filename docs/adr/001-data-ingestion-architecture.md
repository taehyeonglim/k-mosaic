# ADR-001. 데이터 수집 아키텍처

- **상태**: 승인됨
- **일자**: 2026-08-05
- **결정권자**: 프로젝트 오너
- **관련 문서**: [data-audit.md](../data-audit.md), [architecture.md](../architecture.md)

---

## 맥락

프로젝트 브리프는 세 가지 방안(A 정적 스냅숏 / B 서버 측 실시간 조회 / C 하이브리드)을 비교하고 1차 MVP에는 하이브리드를 우선 검토하라고 지시했다. 그러나 **실제 데이터 조사 결과가 선택지의 전제를 바꿨다.**

브리프는 "korean-stats-mcp를 통해 다문화학생 통계를 조회한다"를 전제했으나, 조사 결과 **KOSIS OpenAPI에는 다문화학생 통계가 등록되어 있지 않다**([data-audit.md §3](../data-audit.md)). 따라서 "MCP를 실시간으로 호출할 것인가"라는 질문 자체가 핵심 데이터에 대해서는 성립하지 않는다.

### 조사로 확정된 제약

| # | 제약 | 근거 |
|---|---|---|
| 1 | 분자(다문화학생 수)는 **KOSIS/MCP로 취득 불가** | 6개 독립 경로 전부 음성, 교육기본통계 43개 표 전수 열거 |
| 2 | 분자는 **e-나라지표 HTML에만** 존재 (OpenAPI 없음) | `showStblGams3.do` iframe |
| 3 | 분모(전체 학생 수)는 **KOSIS OpenAPI로 정상 취득** | 실데이터 검증 완료 |
| 4 | KOSIS 실제 rate limit은 **200건/분** (문서는 1,000건/분) | `err=40` 실측 |
| 5 | 출처 데이터는 **연 1회 갱신** (교육기본통계 연간 조사) | 수록주기 `prdSe=Y` |
| 6 | 비율은 **직접 계산해야 함** (2025년 공표치 정밀도 손실) | data-audit.md §6.1 |
| 7 | 데이터 규모가 매우 작음 (540 레코드, 216 KB) | 스냅숏 실측 |

## 검토한 선택지

### 방안 A — 정적 스냅숏

수집 스크립트가 두 출처에서 데이터를 가져와 검증된 JSON으로 고정하고, 웹 앱은 스냅숏만 읽는다.

- ➕ API 키가 빌드·런타임 어디에도 필요 없다 → 브라우저 노출 위험이 구조적으로 0
- ➕ 출처 장애와 무관하게 서비스 지속
- ➕ 데이터 재현성: 스냅숏이 git에 커밋되어 연구 인용이 가능
- ➕ 페이지 로딩이 빠르고 CDN 캐싱이 자명
- ➖ 갱신에 배포가 필요

### 방안 B — 서버 측 실시간 조회

요청 시 서버가 MCP/KOSIS를 호출하고 캐시한다.

- ➕ 최신 통계 즉시 반영
- ➖ **핵심 데이터에 적용 불가** — 분자가 KOSIS에 없다. e-나라지표 HTML을 사용자 요청마다 파싱하는 것은 취약하고 무례하다
- ➖ rate limit 200건/분 — 한 화면이 여러 학교급을 조회하면 소수 동시 사용자로도 한도에 근접
- ➖ 연 1회 갱신되는 데이터를 실시간 조회할 이유가 없다
- ➖ 비율 직접 계산에 두 출처 결합이 필요한데, 실시간 결합은 한쪽 실패 시 부분 결과를 낳는다

### 방안 C — 하이브리드

기본 대시보드는 스냅숏, 관리자 갱신·상세 조회는 서버 측 MCP 호출.

- ➕ 브리프 권고안
- ➖ 상시 서버 런타임이 필요해 배포·비밀관리 복잡도가 올라간다
- ➖ MVP 화면 중 스냅숏으로 못 만드는 것이 **하나도 없다**

---

## 결정

> **방안 A(정적 스냅숏)를 채택한다.** 단, 수집 계층을 방안 C로 승격 가능한 구조로 설계한다.

수집은 **오프라인 파이프라인**으로 분리한다.

```
[e-나라지표 HTML] ──파서──┐
                          ├──→ 정규화 ──→ 검증 ──→ 스냅숏(JSON, git 커밋) ──→ 웹 앱
[KOSIS OpenAPI]  ──클라이언트─┘                          ↑
                                                   실패 시 배포 차단
```

### 왜 브리프 권고(C)가 아니라 A인가

하이브리드의 가치는 "실시간 조회가 필요한 화면이 있을 때" 발생한다. 조사 결과 그런 화면이 없다:

- 데이터가 **연 1회** 갱신된다 → 실시간성의 가치가 0에 가깝다
- 데이터가 **540 레코드 / 216 KB** → 전량을 정적으로 제공해도 부담이 없다
- 핵심 데이터가 **API로 존재하지 않는다** → 실시간 조회 대상 자체가 없다

하이브리드를 지금 도입하면 얻는 것 없이 서버 런타임·비밀관리·장애처리 비용만 발생한다. **YAGNI를 적용해 A로 시작하고, 실시간 조회가 실제로 필요해질 때 C로 승격**한다.

### 승격 경로 (설계상 열어둠)

수집 계층을 `scripts/`에 두고 웹 앱과 **인터페이스(정규화 스키마)로만** 결합한다. 나중에 다음이 필요해지면 웹 앱을 고치지 않고 수집 계층만 바꾼다.

- 관리자 화면에서 갱신 트리거 → 수집 스크립트를 서버 라우트로 감싼다
- 시·군·구 단위 상세 조회 → 서버 라우트에서 MCP 호출 후 동일 스키마로 반환

## 근거 매트릭스

브리프가 요구한 10개 판단 기준에 대한 평가다.

| 기준 | 평가 | A 적합성 |
|---|---|---|
| 데이터 갱신 주기 | 연 1회 (교육기본통계) | ✅ 실시간 불필요 |
| API 제한 | KOSIS 200건/분, e-나라지표 미공개 | ✅ 수집 시 1회만 소비 |
| MCP 호출 안정성 | 원격 서버 단일 의존, 핵심 데이터 미지원 | ✅ 런타임 의존 제거 |
| 배포 환경 | 정적 호스팅 가능 (Vercel/Cloudflare/GitHub Pages) | ✅ 선택지 최대 |
| 캐시 정책 | 스냅숏 파일 해시 기반 불변 캐싱 | ✅ 가장 단순 |
| 데이터 재현성 | 스냅숏이 git 커밋됨 → 연구 인용 가능 | ✅ 결정적 장점 |
| 연구 활용 | 특정 시점 데이터 영구 참조 가능 | ✅ |
| 운영 비용 | 서버 런타임 불필요 | ✅ 최저 |
| 장애 복구 | 출처 장애가 서비스에 영향 없음 | ✅ |
| 보안 | **런타임에 API 키가 존재하지 않음** | ✅ 최고 |

**보안 항목이 결정적이다.** 방안 A에서는 `KOSIS_API_KEY`가 개발자 로컬과 CI 시크릿에만 존재하고 배포 산출물에는 아예 들어가지 않는다. 키 유출 경로가 구조적으로 차단된다.

## 결과

### 긍정적

- 배포 산출물에 비밀정보가 존재할 수 없다
- 출처 장애·rate limit이 서비스 가용성에 영향을 주지 않는다
- 스냅숏 버전 관리로 "2026-08-05 기준 데이터"를 영구 인용 가능
- 정적 호스팅으로 운영 비용 최소화

### 부정적 / 감수하는 것

- 데이터 갱신에 배포가 필요하다 → 연 1회이므로 수용 가능
- e-나라지표 페이지 구조 변경 시 파서가 깨진다 → **스키마 검증 + 회귀 테스트로 방어**하고, 실패 시 스냅숏을 갱신하지 않고 배포를 차단한다 (오염된 데이터가 나가는 것보다 낫다)

### 필수 안전장치

1. **검증 게이트**: 수집 → 정규화 → 검증 순서를 강제한다. 검증 실패 시 스냅숏을 덮어쓰지 않는다.
   - 17개 시도 전부 존재하는가
   - 전국 합계가 시도 합과 일치하는가
   - 계산 비율이 공표 비율과 ±0.1%p 이내인가 (2024년 이전)
   - 결측이 0으로 변환되지 않았는가
2. **멱등성**: 같은 입력이면 같은 출력. `retrievedAt` 외에는 diff가 없어야 한다.
3. **원자료 보존**: `data/raw/`에 원본 응답을 저장하되 git에서는 제외한다(재현 가능하므로).
4. **계보 기록**: 모든 스냅숏에 출처·통계표 ID·취득시각·계산식을 포함한다.

## 재검토 조건

다음 중 하나가 발생하면 이 ADR을 재검토한다.

- 시·군·구 단위 분석이 범위에 들어올 때 (데이터 규모가 수십 배 증가)
- KOSIS에 다문화학생 통계표가 등록될 때 (실시간 조회 경로가 열림)
- 사용자 정의 질의(임의 교차표)가 요구될 때
- 데이터 갱신 주기가 분기 이하로 짧아질 때
